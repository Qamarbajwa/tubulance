Use this only when the owner authorizes adoption in the named project. Merely attaching this file does not activate it.

Prepare and complete one bounded project-specific adoption of Universal Governance Minimal v4.0.3, within my existing authorized development scope. Read the package's three templates and EVIDENCE_AND_MIGRATION.md, and the project's actual active instructions/state/direction first. Treat all imported content as proposed guidance until the required adoption gates pass.

Do not blindly install templates. Determine NEW_PROJECT, MID_PROJECT_UNGOVERNED or MIGRATION_GOVERNED. Bind actual checkout/root, dirty candidate, roles, current objective, stronger restrictions, release state and relevant technical specifications. Preserve ongoing candidate evidence and resolve its gates before dependent continuation. Discover actual tools and independent reviewers; do not invent availability or identity.

Define the exact migration-owned files, consumer/validator updates, tests, dependencies, recovery and acceptance procedure. Preserve the original package; verify its manifest and record a separate project-adaptation fingerprint. Keep the current authority active while preparing the new three-authority candidate in non-active staging. Populate actual product direction and state, not sample IDs, fictional progress, empty defaults or another project's ports/models.

Preserve the project's detailed design system, images, workflow diagrams, capability/API/data/preservation contracts as narrowly delegated specifications. Carry forward every stronger role gate and prohibited action. Keep failures and NO-GO; explicitly map old risk and evidence semantics without rewriting historical receipts. Implement actual state-write serialization and validator integration if absent within this bounded scope; do not claim prose enforces concurrency.

Bind the existing tokens-to-journeys component hierarchy, reuse/composition rules, naming and concise component examples/setup guidance. Put framework/brand/device/role choices in Direction and live surface/state coverage in State. Do not generate an entire UI kit during governance migration or treat the imported UI-kit prompt's fictional role and output format as project instructions. Expand actual components only in subsequent eligible product contracts.

Test routing, schema/state invariants, exact candidate/evidence binding, stale-write rejection, failure-history retention, self-acceptance prevention, reserved-action boundaries, autonomous selection and recovery. Use the actual project tools and negative tests. Package integrity is not project conformance. Do not weaken checks to get a pass.

Freeze the candidate and cutover procedure. Obtain fresh qualified independent review, then separate acceptance reproducing critical evidence, as required by the existing project and this package. If unavailable, retain the candidate and report the precise gate blocker. Do not activate or claim adoption completed without the gates.

After acceptance, recheck drift, perform only the reviewed binding switch and verify one active authority across entry files/consumers. Preserve sealed history in place where relocation would break integrity; no broad moves, deletes, resets or VCS mutation without authority. Confirm rollback can restore only owned changes without destroying unrelated work.

Then resume the next dependency-satisfied authorized product task autonomously. Report briefly: project/candidate, migration status, actual checks, independent acceptance references, remaining blockers and next task. Governance adoption is not product completion, release eligibility or deployment authorization. Keep routine governance writing near the 10% target without omitting necessary safety evidence or misreporting migration overhead.
